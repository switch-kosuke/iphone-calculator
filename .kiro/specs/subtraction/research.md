# ギャップ分析レポート：subtraction

---
**目的**: 引き算機能の要件と既存コードベースの差分を分析し、設計フェーズへの入力を提供する

---

## サマリー

- **フィーチャー**: `subtraction`（引き算）
- **調査スコープ**: Extension（既存コンポーネントの拡張）
- **主要発見**:
  - `CalculatorEngine.calculate()` は `'+'` のみ処理、`'-'` は `NaN` 返却 → **1行追加で対応可能**
  - `handleOperator()` はすでに任意の演算子文字列を受け付ける設計 → **変更不要**
  - HTML グリッドの行 2・3・4 の第4列（演算子列）が `<div></div>` プレースホルダー → **−ボタン追加が必要**
  - `index.js` の `render()` のオペレーターハイライトが `+` にハードコード → **汎用化が必要**
  - キーボードハンドラで `'-'` キーが未処理 → **追加が必要**

---

## 1. 現状調査

### 既存アセットと統合ポイント

| ファイル | 役割 | 変更の必要性 |
|----------|------|-------------|
| `calculator-state.js` | 演算エンジン・状態管理 | **あり**（`calculate()`に`'-'`追加） |
| `index.html` | ボタンレイアウト | **あり**（−ボタン追加） |
| `index.js` | イベント登録・レンダリング | **あり**（リスナー追加・ハイライト汎用化・キー対応） |
| `calculator-view.js` | ビュー予約（空） | なし |
| `test-engine.js` | エンジン単体テスト | **あり**（減算テスト追加） |
| `test-state.js` | 状態フロー単体テスト | **あり**（減算フローテスト追加） |

### アーキテクチャ制約

- **DOM非依存原則**: `calculator-state.js` はDOM参照なし → テスト容易性を維持するため、新ロジックもこの原則に従う
- **グローバル関数パターン**: 状態管理は `handleXxx(state, ...)` 形式の純粋関数 → `handleOperator` をそのまま流用できる
- **CommonJS 条件分岐**: `if (typeof module !== 'undefined') module.exports = {...}` → exports に新関数を追加する場合も同パターンを踏襲

| Req 1: −ボタンUI | `<div></div>` プレースホルダー (行2-4第4列) | HTMLに−ボタン要素が存在しない | **Missing** |

## 3. 実装アプローチの評価

### Option A: 既存コンポーネントの拡張（推奨）

既存のファイル構成・パターンをそのまま活用し、各ファイルに最小限の追加を行う。

**変更箇所**:
1. `calculator-state.js` — `calculate()` に `'-'` ブランチ追加（1行）
2. `index.html` — 行2・3・4の第4列 `<div>` を `−` ボタンに置き換え（ただし iOS電卓の配置では行3に相当する位置）
3. `index.js` — `btn-subtract` のイベントリスナー追加、`render()` のハイライトロジックを現在のアクティブ演算子に対して動的に判定するよう汎用化、`'-'` キー対応追加
4. `test-engine.js` / `test-state.js` — 減算テストケース追加

**トレードオフ**:
- ✅ 新規ファイル不要、パターン踏襲
- ✅ `handleOperator` の再利用で状態管理コード変更最小
- ✅ 浮動小数点補正パターン（`toPrecision(12)`）が既存実装にそのまま適用可能
- ❌ `render()` のハイライトロジックが演算子数の増加とともに条件分岐が増える可能性（ただし今回のスコープでは問題なし）

### Option B: 汎用的なオペレーターシステムの新設

演算子ボタンを動的に管理するマップ（`OPERATORS = { '+': {...}, '-': {...} }`）を導入し、ボタン登録・ハイライト・キー対応を一元管理する。

**トレードオフ**:
- ✅ 将来の演算子追加（×、÷）時の拡張性が高い
- ❌ 今回の要件スコープに対して過剰設計（YAGNI 違反リスク）
- ❌ 既存の明示的なボタンID管理パターンとの乖離

### Option C: ハイブリッド（Option A + 部分的なリファクタリング）

Option A を基本とし、`render()` のハイライトロジックのみをヘルパー関数化する。

**トレードオフ**:
- ✅ ハイライトロジックのテスタビリティが向上
- ❌ `calculator-view.js`（現在は空）との役割整理が必要になる可能性

## 5. 設計フェーズへの推奨事項

**推奨アプローチ**: Option A（既存コンポーネントの拡張）

**設計フェーズで決定すべき主要事項**:

1. **−ボタンの配置位置**: iOS電卓では `−` は行2第4列（7,8,9 の右）。現在その列は `<div>` プレースホルダー。既存の `+` ボタン（行4第4列）との位置関係を確認した上で配置を決定する。
2. **`render()` ハイライトロジックの汎用化方法**: 単純な条件追加か、アクティブ演算子IDを動的に解決するかを設計で明確化する。
3. **ボタンIDの命名**: `btn-subtract` が既存の `btn-add` パターンに合致することを確認。

**リサーチ不要の確定事項**:
- `toPrecision(12)` による浮動小数点補正は減算にも適用可能（既存パターンの流用）
- キーボードの `'-'` キーは `e.key === '-'` で検出可能（既存の `+` と同じパターン）
- CommonJS `module.exports` は既存の条件分岐パターンで対応済み

---

## リスクと緩和策

- **HTML グリッド崩れ**: `<div>` を `<button>` に置き換える際、`grid-cols-4` レイアウトに影響しないよう既存ボタンのクラスをコピーすること
- **既存テスト回帰**: `CalculatorEngine.calculate()` の変更で既存の `+` テストが影響を受けないことを確認してからマージする
